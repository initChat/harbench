01Goal, and where this sits in the pipeline

Question this material answers: given an unseen target HAR dataset, which subset S of baseline datasets and per-baseline mixture weight w should a pretrained SSL backbone be finetuned on, and how is "the winner" mathematically determined — while guaranteeing the reported number was never seen by any search decision?

lightweight-score-unify heavyweight-similar-score (signal-quality gate) (target-similarity rank) │ │ └───────────┬──────────────┘ ▼ optimal_subset_selection (sibling repo, orchestrator) semantic_scorer → features → candidate_pool/llm_proposer → surrogate (GP+UCB) → reward_combined → winner │ shells out per candidate, real trial ▼ harbench/finetune.py (THIS REPO) --loss_mode ce_scl pooled trial (search-time, many times) run_finetune_multi_candidate (confirmatory, once) │ ▼ held-out honesty check (never searched over)

harbench is the execution engine: it never decides which candidate to try next or which one wins — that logic lives in the sibling repo optimal_subset_selection. harbench is trusted to (a) train a specific manifest correctly and (b) enforce the train/val/test user partitions that make every number it returns honest. This deck documents both halves — the upstream decision math (cross-repo, read from source, not imported) and harbench's own splitting code — because a methodology section needs both to describe the experiment precisely.

02The selection cascade — every equation, in pipeline order

Six independent scores/decisions compose into "is (S, w) selected as the next trial" and "is trial t selected as the winner." Each stage names its owning repo — only the last two run inside harbench itself.

Stage A — Signal-quality gate cross-repo

Repo: lightweight-score-unify. Per (user, sensor-location) row r, for each metric m with fixed absolute anchors (bad_m, good_m) (no peer comparison):

score_m(r)                 = clip( (value_m(r) - bad_m) / (good_m - bad_m), 0, 1 )
unify_lightweight_score(r) = mean_m score_m(r)               # lightweight_check.py:204-209

unified_lightweight_score(D) = mean_r unify_lightweight_score(r)   # lightweight_check.py:224-232

Gate (population P = every previously-scored dataset's score, μ = mean(P), σ = std(P)):

D passes  ⟺  unified_lightweight_score(D) ≥ μ − 3σ            # lightweight_check.py:411-431

cross-repo A one-tailed 3σ historical-outlier rule, not a fixed absolute cutoff. harbench's side only reads this gate's pass/fail JSON as data (optimal_subset_selection/lightweight_pool.py:37-46) — never recomputes or imports the scoring code.

Stage B — Target-similarity re-scoring cross-repo

Repo: heavyweight-similar-score. For each baseline i that passed Stage A, against fixed target T, pairwise silhouette(T,i)/mmd(T,i) on L2-normalized 512-d embeddings, leave-one-out z-scored against the other passed baselines:

z_i  = ( x_i − mean_{j≠i}(x_j) ) / std_{j≠i}(x_j)
low_clip:  s_i = ( clip(−z_i, −σ, σ) + σ ) / (2σ)              # scoring.py:4-6,31-46,93-98

heavyweight_score(T, i) = mean( s_silhouette(i), s_mmd(i) )    # scoring.py:101-119

"only_sh_mmd branch": two other metrics this module defines (effective_rank, temporal_coherence) are deliberately unhooked from the score. harbench's neighbor consumes this as a pre-rendered markdown rank table, never re-derives it.

Stage C — Semantic compatibility cross-repo

Repo: optimal_subset_selection, LLM-scored. activity_semantic_score(i), placement_semantic_score(i,p) ∈ [0,1] — not closed-form: one forced-tool-use Claude call per target run (semantic_scorer.py:180-279), clipped via _clip01 (line 176-177). Its inputs are exact, not semantic: shared_activities/target_activities_uncovered are plain set intersection/difference over taxonomy-canonicalized labels (_shared_and_uncovered, lines 111-117) — the LLM judges only the compatibility those sets can't answer alone.

Stage D — Empirical baseline score

empirical_baseline_score(i) = (1 / |{t : i ∈ S_t}|) · Σ_{t : i ∈ S_t} macro_f1(t)   # features.py:60-76

Over every real trial t run so far in either phase. Falls back to the neutral constant 0.5 if i has never appeared in a trial (features.py:38,90-91,117-119) — the one feature that can only reflect behavior after real trials exist.

Stage E — Portfolio feature vector (the GP's input)

weighted_mean(v; S, w) = Σ_k w_k · v.get(i_k, 0.5)  /  Σ_k w_k             # features.py:41-43

features(S, w) = [ weighted_mean(heavyweight_score),
                    weighted_mean(activity_semantic_score),
                    weighted_mean(placement_semantic_score),
                    weighted_mean(empirical_baseline_score) ]  ∈ ℝ⁴        # features.py:31-36,79-126

Deliberately just these four means — no cost term, no portfolio-shape statistics (task-doc decision, features.py:26-28).

03Candidate generation — how (S, w) is produced

Two disjoint mechanisms, split by config.ITER_LLM_END = 30 (1-indexed):

Iterations 1–29 — LLM phase

One candidate per iteration, from a forced-tool-use LLM call conditioned on every baseline's frozen Stage A/B/C facts plus the running trial log (llm_proposer.py, dispatched at loop.py:136-145). Not a closed-form rule.

Iterations 30+ — BO phase, uncapped for the rest of the run

Ω = ⋃_{s=1}^{k}  C(B, s)     (B = eligible baseline pool, |B|=n, k=max_subset_size, default 4)
                                                              # candidate_pool.py:60-68

Guarded before enumeration by math.comb (MAX_POOL_PORTFOLIOS = 1e8, lines 135-176) — a real 2026-08-25 incident: an uncapped 44-baseline pool is 2^44 ≈ 1.8×10^13 subsets and OOM-killed the host.

w ~ Dirichlet(1,…,1)     (uniform over the (n−1)-simplex), up to n_weight_draws=3
kept only if L∞(w, every prior kept draw) > MIN_WEIGHT_DIFF = 0.03          # candidate_pool.py:83-103

|S|=1 always yields w=[1.0]. Seed is deterministic per-subset (md5(f"{seed}:{subset}"), lines 75-80) — reproducible given the same eligible-baseline list.

04The reward — the scalar every trial is judged by

reward(mean_f1, std_f1; κ=0.5)               = mean_f1 − κ·std_f1                # surrogate.py:29-34
reward_per_class(pcf1; κ=0.5, worst_class)   = min_c(pcf1[c]) − κ·std(pcf1_std)   # surrogate.py:37-57
reward_combined(macro_f1, per_class_f1; α=0.5, κ=0.5)
    = α·macro_f1 + (1−α)·min_c(per_class_f1[c]) − κ·std_f1                        # surrogate.py:60-74

min over classes, not mean: mean(per_class_f1) is by definition the same number as macro-F1, so blending macro-F1 with the mean of per-class F1 would be degenerate. min is the one per-class quantity that actually diverges. α = config.REWARD_MACRO_WEIGHT = 0.5 is an untuned equal-weight default. This is the one scalar logged for every iteration in both phases (loop.py:204-218).

macro_f1 and every per_class_f1[c] come from harbench's own evaluate(), restricted to the target dataset's own label ids (finetune.py:339-357,403-417; ids resolved by _resolve_target_label_ids, lines 954-964) — a fix over an earlier bug where scoring against the full pooled taxonomy diluted macro_f1 by how many baselines got pooled, not by target performance (commits 19b05f0, 444c92f).

05Selection I — which candidate runs next (acquisition)

BO-phase only. Fit a GP on every previously-tried candidate's (features, reward_combined):

g ~ GaussianProcessRegressor( kernel = RBF(ℓ=1, fixed) + WhiteKernel(1e-3),
                               normalize_y=True, n_restarts_optimizer=0 )         # surrogate.py:83-95

Deliberately untuned — "a proof the mechanism works... not a statistically tuned model at the trial counts this repo runs" (surrogate.py:1-8).

(μ_c, σ_c) = g.predict(x_c, return_std=True)
UCB(c) = μ_c + κ_UCB · σ_c ,    κ_UCB = KAPPA_UCB = 1.0
chosen = argmax_c  UCB(c)                                                         # surrogate.py:26,98-124

Cold start (empty history) instead ranks by mean_heavyweight_score alone (bootstrap_rank, lines 77-80) — in practice the LLM phase always populates history first. mean_empirical_baseline_score (Stage D) is recomputed every BO iteration, not cached at pool-build time — a baseline shown toxic at iteration 33 discourages re-picking it at iteration 40 (loop.py:152-158).

06Selection II — which trial is the winner

winner = argmax_{t ∈ trial_log}  reward_combined(t)          # loop.py:224-229

Across both phases pooled together — an early LLM-phase trial can beat every later BO-phase trial. Dict key kept as "best_by_macro_f1" for an external JSON contract even though the ranking criterion is the full blended reward — read that key name as legacy, not literal.

This is still a search-time number, computed on the search-view (held-out subjects physically absent from disk) — explicitly not reportable (finetune.py:1319-1321: pooled_search_time_macro_f1 is "kept for reference only"). Section 7c covers the confirmatory step that produces the number that is reportable.

07User-role assignment — the equations and rules

Every reported F1/accuracy number is only as trustworthy as the user split that produced it. Three independent, fully deterministic rules apply, selected by run mode — no rule ever draws a random train/test split per run; every split is a fixed lookup table or a seeded reproducible draw.

7a. Single-dataset 4-fold CV (run_finetune, default mode)

FOLDS = [
    {"test": [1, 2], "val": [3, 4]},
    {"test": [3, 4], "val": [5, 6]},
    {"test": [5, 6], "val": [7, 8]},
    {"test": [7, 8], "val": [1, 2]},
]                                                              # finetune.py:159-164

SEED = 42 (line 157) seeds everything else — model init, sampler shuffling — not this table, which is fixed. train = ~(test_mask ∪ val_mask), computed once in the shared loader (src/data/dataloader.py:441-443), not enumerated separately.

verified live Every subject id 1..8 serves as test in exactly one fold and val in exactly one fold. Any subject id beyond 8 is in train in every single fold — never tested, in any fold. held_out.py's own docstring confirms this cross-repo: "harbench's FOLDS only ever rotates subjects 1-8 through test/val roles; every dataset's subjects beyond #8 are already used for TRAINING in every fold" (held_out.py:5-7).

7b. Pooled multi-baseline training (run_finetune_pooled, and the pooled half of run_finetune_multi_candidate)

_pooled_train_val_test_masks (finetune.py:911-951, shared by both call sites — one implementation). Per pooled dataset d with raw ids sorted ascending r_1 < r_2 < … < r_m:

if m ≥ 4:   test(d) = {r_1, r_2}      val(d) = {r_3, r_4}      train(d) = {r_5,…,r_m}
if m < 4:   per-user split impossible → random per-window fallback (below)

Position-based, not literal-id-based — the deliberate fix over a bug where FOLDS[0]'s literal ids [1,2]/[3,4] silently produced an empty split for any dataset not numbered 1..8 (e.g. har70plus uses raw ids 501..518); see commit d5e8b2f and finetune.py:1013-1025.

perm = RandomState(SEED=42).permutation(all_window_indices_of_d)
n_test = max(1, round(N · 0.2))     n_val = max(1, round(N · 0.2))
test(d) = perm[:n_test]   val(d) = perm[n_test : n_test+n_val]   train(d) = rest
                                    # WINDOW_SPLIT_{TEST,VAL}_FRAC=0.2, finetune.py:169-170,935-944

Window-level fallback applies only to a pooled dataset with <4 distinct users, and is not subject-independent for that dataset (windows from the same subject can land in both train and test) — an explicit, named limitation (finetune.py:1022-1025). It applies per affected dataset only; every other pooled dataset in the same manifest still gets 7b's subject-independent split.

7c. Permanent held-out subjects cross-repo

Repo: optimal_subset_selection, consumed by harbench via --custom_test_users/--custom_val_users.

FOLDS_SUBJECT_IDS = {1,…,8}                                   # held_out.py:33, mirrors 7a's domain

held_out(T) = the 2 lowest-id subjects of T with raw id ∉ FOLDS_SUBJECT_IDS
val(T)      = the next 2 lowest-id subjects of T with raw id ∉ FOLDS_SUBJECT_IDS ∪ held_out(T)
                                                    # pick_held_out_subjects/pick_val_subjects, held_out.py:36-60

Deterministic — "the lowest-id ones among the spare pool, for reproducibility," not random.

search_view(T) = symlink view of T's on-disk USER folders with held_out(T) excluded   # held_out.py:63-68

cross-repo Every search-time trial (every LLM- or BO-phase candidate) is pointed at search_view(T) via manifest_builder.build_manifest's target_entry — held_out(T) is structurally absent from training data for the entire search, not merely excluded by an id filter a bug could bypass.

Final honesty check — run exactly once, after the search picks a winner, on the full, unfiltered data root:

harbench finetune.py --single_split \
    --dataset T --data_root <FULL root, not search_view> \
    --weights <winner's finetuned backbone> \
    --custom_test_users {held_out(T)} --custom_val_users {val(T)}
                       # held_out.py:86-124; finetune.py:1216-1217,1226-1241 (multi-candidate variant)

This is the only evaluation in the whole pipeline that never influenced a single search decision — it is the number that belongs in a paper's results table, not pooled_search_time_macro_f1 (§6) and not the LLM/BO reward.

--custom_test_users/--custom_val_users (finetune.py:1828-1834) override FOLDS[0]'s ids for single-split mode — validated to require --single_split (or --candidates_manifest_json) and to always be given as a pair (finetune.py:1862-1881).

7d. Mixture-weight realization changes who is physically present in train

Repo: optimal_subset_selection. weighted_pool.build_weighted_view realizes a non-uniform w_i by dropping whole user folders (never partial-user rows), since harbench's pooled loader has no weighting concept of its own:

scale_factor = min_i( natural_i / w_i )          # largest pool achievable by pure down-sampling
target_i     = scale_factor · w_i                                    # weighted_pool.py:60-66

A greedy, folder-name-sorted selection keeps users until the running total is closest to target_i, never below MIN_USERS = 4 kept users (lines 69-92,33) — that floor exists so 7b's ≥4-users branch still applies after down-sampling. A small w_i shrinks baseline i's train contribution only — its test/val users are still chosen by 7b's position-based rule on whichever users remain in the view.

08Control flow — run_finetune_multi_candidate (finetune.py:1144-1340)

The one harbench-native function tying §4–7 together for a single target, replacing optimal_subset_selection/candidate_ablation.py's older 2·(N+1)-subprocess orchestration with one process:

1. Load target data once

finetune.py:1212-1217 — load_dataset reads the target's full, non-search-view root (held-out subjects must be physically present so --custom_test_users can exclude and later test on them). Reused for every held-out-eval call below.

2. prior_backbone baseline

finetune.py:1219-1241,1302-1306 — _held_out_eval on the un-finetuned pretrained backbone: plain CE single-split fine-tune on train = all \ (held_out ∪ val), test only on held_out. The pre-search reference point.

3. Per candidate cid in the manifest list

finetune.py:1243-1300,1308-1325 — _train_pooled_candidate rebuilds the same CE+SCL pooled trial §4–6 already ran during search (set_seed re-called before every stage — one process now runs what used to be separate subprocesses, so RNG state must be reset explicitly), using the 7b split, logging pooled_search_time_macro_f1 for reference only; then _held_out_eval on the resulting finetuned backbone — the 7c honesty check, on the SAME held-out subjects as step 2.

4. Write results.json

finetune.py:1327-1340 — one row per candidate: {candidate_id, baselines: dict(zip(S, w)), test_f1, test_acc, pooled_search_time_macro_f1, ...}. This is exactly the file shape a finetune_multi_candidate/.../results.json run produces.

Determinism note (finetune.py:1169-1176): every stage explicitly calls set_seed(args.seed) and does del model + torch.cuda.empty_cache() — a fresh subprocess used to get a fresh seed/fresh GPU memory for free; running 2·(N+1) models sequentially in one process makes both an explicit responsibility instead.

10Assumptions baked into the code (and where they'd break)

  • 7a's FOLDS assumes raw subject ids 1..8 exist and mean "the canonical rotation set." Any dataset numbered differently either silently ignores subjects >8 for testing forever (7a) or would have produced an empty split before the 7b fix — now guarded (d5e8b2f, and create_dataloaders's loud ValueError at src/data/dataloader.py:455-466).
  • 7c's held-out/val picks assume ≥4 spare subjects outside FOLDS_SUBJECT_IDS per target. held_out.py:41-46,55-60 raises ValueError rather than degrading — no window-level fallback the way 7b has one.
  • reward_combined's α=0.5/κ=0.5 are untuned defaults, not fit to any validation criterion (config.py:70-72) — cite these as fixed hyperparameters of the search, not learned values.
  • The GP kernel is deliberately fixed/untuned (length_scale_bounds="fixed", n_restarts_optimizer=0) — "a proof the mechanism works... not a statistically meaningful surrogate at the trial counts this repo runs" (surrogate.py:1-8).
  • weighted_pool's down-sampling never drops below 4 survivors, so an achieved mixture weight can be off from the requested one for a small baseline — manifest_builder reports both requested and achieved weight rather than assuming they match.
  • pooled_search_time_macro_f1 is not an honesty check — held-out excluded, but not independent of the acquisition process that chose the candidate. Explicitly flagged non-reportable (finetune.py:1319-1321); only §7c's number is valid.

11How to verify this deck's claims yourself

No pytest-based test in harbench exercises the cross-repo selection math directly — that lives in optimal_subset_selection/tests/ (python tests/run_all.py, mocking the real LLM/subprocess calls). To sanity-check harbench's own splitting code in isolation:

python -c "
from src.data.dataloader import load_dataset, create_dataloaders
X, Y, U = load_dataset('dsads', ['ACC'])
tl, vl, tel = create_dataloaders(X, Y, U, [1,2], [3,4])
print(len(tl.dataset), len(vl.dataset), len(tel.dataset))"

Confirm the three counts partition len(U) with no overlap (train_mask = ~(test_mask | val_mask) guarantees this algebraically; a live run also catches a silently-empty split via the ValueErrors at src/data/dataloader.py:455-466). For the full multi-candidate flow, run run_finetune_multi_candidate with a tiny one-candidate manifest and --epochs 1, and confirm results.json has exactly 1 + len(candidates) rows with distinct weights_paths.

12How to maintain this

  • Change the reward function: edit surrogate.py's reward_combined only — loop.py/finetune.py never hardcode the formula. Update config.REWARD_MACRO_WEIGHT for the blend weight, not a literal in surrogate.py.
  • Change held-out/val reservation counts: held_out.py's reserve_target(n_held_out=2, n_val=2) — but harbench's 7a/7b rules independently assume 2 test + 2 val per fold/dataset; changing one without the other desyncs which subjects are "spare."
  • Change the BO candidate pool's size: candidate_pool.py's max_subset_size/n_weight_draws — always re-check _estimate_portfolio_count against MAX_POOL_PORTFOLIOS first. harbench has no cap of its own — it trusts whatever manifest it's handed.
  • Change held-out/val selection strategy (e.g. stratify instead of lowest-id): only held_out.py's pick functions need to change; harbench's --custom_test_users/--custom_val_users contract is agnostic to how ids were chosen.
  • Change the pooled test/val split (7b): touch _pooled_train_val_test_masks only — shared by run_finetune_pooled and run_finetune_multi_candidate specifically so this rule has exactly one implementation; do not fork it per call site.

Appendix — methodology-section-ready summary

For each target dataset, baseline datasets are first screened for signal quality (a per-dataset score in [0,1], gated at mean − 3σ over the historical score population) and then re-ranked against the target by a leave-one-out z-scored blend of embedding silhouette and MMD. A search procedure — 29 LLM-proposed iterations followed by Gaussian-process/UCB optimization over a mechanically enumerated subset-and-Dirichlet-weight pool (subset size ≤ 4, ≤ 3 weight draws per subset) — evaluates each candidate (S, w) with a real cross-entropy + supervised-contrastive finetuning trial, scored only on the target dataset's own classes. Every trial is reduced to reward = 0.5·macro-F1 + 0.5·worst-class-F1, and the maximum-reward trial across both search phases is selected as the winning recipe. Two subjects per target dataset (the lowest-numbered subjects outside the standard 4-fold rotation's {1,…,8}) are permanently reserved and physically excluded from every search-time dataset view; after the search concludes, the winning recipe's finetuned backbone is re-evaluated exactly once against these held-out subjects, and this number — never seen during search — is reported.

Adjust the constants (α=0.5, κ=0.5, κ_UCB=1.0, 29/30 iteration split, 2 held-out + 2 val subjects, subset cap of 4) to whatever values a given run actually used — every one is a named constant in config.py/surrogate.py, not hardcoded inline, so a specific run's exact values are recoverable from its logged config.
